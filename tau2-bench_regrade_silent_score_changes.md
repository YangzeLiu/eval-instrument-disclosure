Title: `evaluate-trajs` lenient replay re-grades `llm_agent_solo_gt` telecom files from 0.72 to 0.10 with no error; plus `--fresh-tasks` criteria drift, unparseable leaderboard files, and independent confirmation of the 1.0.1 banking re-grade

**Context.** We re-graded public trajectory files (repository examples and the S3 leaderboard set) under four builds side by side: 0.2.0, 1.0.0, the commit before 1.0.1, and 1.0.1, crossing evaluator code with task data via `PYTHONPATH` and `TAU2_DATA_DIR`. Fidelity check on banking, claude-opus-4-5: pre-1.0.1 pass^1 0.2135 vs official 0.2139; 1.0.1 pass^1 0.2474 vs official 24.74, exact.

**1. Telecom `llm_agent_solo_gt` files re-grade to a fraction of their recorded score, with no error.** `evaluate-trajs` passes `strict_replay=False` unconditionally (`src/tau2/scripts/evaluate_trajectories.py:133`); the underlying default is strict (`Environment.set_state(..., strict: bool = True)`, `src/tau2/environment/environment.py:293`) and live evaluation stays strict, but there is no CLI flag to restore strict re-grading. The same function decides solo mode with `is_solo_mode()` (`evaluate_trajectories.py:20-26`), which matches only `agent_implementation == "llm_agent_solo"` together with `dummy_user`. The four repository telecom files recorded with **`llm_agent_solo_gt`** therefore fall through to `solo_mode=False`, and `telecom.get_environment(solo_mode=False)` (`src/tau2/domains/telecom/environment.py:99, 108, 144-145`) never calls `set_solo_mode(True)`, so the user-side `TelecomUserTools` are absent from the replay environment. Every replayed user-side call then returns `Error: Tool 'toggle_roaming' not found.` Strict replay raises on the first one; lenient replay logs a warning per call and continues against an environment that never received those mutations.

Running the official CLI today on the repository's own 0.2.0 `no-user-op` telecom file:

- pre-1.0.1: the whole file aborts (`Error processing file`, 0 files processed, 1 failed). Our per-simulation harness, which catches the exception per simulation rather than per file, marks 92 to 100% of simulations unscorable across the four files.
- 1.0.1: all 456 simulations are scored, DB match falls to 3 of 456 (0.7%), and pass^1 reports **0.0965** against the file's own recorded **0.7215**. Across the four files the recorded values 0.7478, 0.7215, 0.9035 and 0.9890 become 0.1601, 0.0965, 0.1754 and 0.1732.

The control is decisive: the companion `no-user` file, which records `llm_agent_solo` and so *is* recognised by `is_solo_mode()`, re-grades to its recorded 0.5154 under both builds. Only the `llm_agent_solo_gt` files collapse, and the collapse is a misclassification rather than a grading disagreement. Issue #387 makes the argument for us from the other direction: its reporter closed it saying that the evaluator raising on a replay mismatch is what caught their bug. We recognise why leniency was introduced (#273), and note that PR #393 would move further the same way by having evaluator exceptions return `reward=0.0`; the request below is not to abort a batch, it is to report the mismatch count.

**2. `--fresh-tasks` applies the 1.0.0 airline criteria rewrite to older trajectories, moving scores in both directions.** With embedded tasks, pre-1.0.1 and 1.0.1 agree on all 22 files that are not `llm_agent_solo_gt` (about 9,000 simulations, 0 flips). With `--fresh-tasks`, airline picks up the 1.0.0 `tasks.json` edit while `db.json` and `policy.md` stay byte-identical. All 50 airline tasks have a modified `evaluation_criteria` block, but 36 of them differ only by an explicitly written `reward_basis: ["DB", "COMMUNICATE"]`, which is exactly the pre-existing code default (`src/tau2/data_model/tasks.py:426-437`, and already the default at 0.2.0), so those are grading no-ops. **14 tasks carry substantive changes to `actions`, `nl_assertions` or `communicate_info`: ids 2, 5, 7, 9, 13, 14, 23, 27, 29, 33, 35, 37, 38 and 44.** On the four 0.2.0-era airline files (800 simulations) the rewrite flips 86 simulations, from -7.00 to +2.50 points per model, and reverses the order of gpt-4.1-mini and claude-3-7-sonnet. The 1.0.0 CHANGELOG lists the 27 airline task fixes but has no comparability warning like the one attached to banking in 1.0.1. `code100fresh` and `code101fresh` are identical on airline, so the 1.0.1 note that other domains are unaffected is correct; the airline movement is 0.2.0 to 1.0.0. Separately, `--fresh-tasks` was added in 1.0.1 (CHANGELOG L43) but is missing from `docs/cli-reference.md:187-200`, which documents only `<paths>` and `-o`.

**3. Two banking leaderboard trajectory files still do not parse, and the repair described in PR #408 has not reached the published artifacts.** PR #408 records that four externally submitted trajectory sets (`glm-5-think`, `qwen3.5-397b-a17b-think`, `gemini-3-pro`, `gemini-3-flash`) were uploaded without tool-message `id` fields, that the ids were restored positionally, and that the files were then re-graded. Of those four, the `gemini-3-pro` and `gemini-3-flash` files we downloaded parse; the `glm-5-think` and `qwen3.5-397b-a17b-think` files still have tool messages without an `id` and cannot be loaded by any build, which suggests a partial re-upload. The consequence is not that the scores are wrong, it is that the re-grade of those two submissions is not reproducible from public data. (These are also the two submissions in the 17-entry comparison set whose official pre-1.0.1 to 1.0.1 delta is exactly 0.00; on the full board `glm5-2` and `distyl-buttonagent` are 0.00 as well. And `RELEASE_NOTES.md` already discloses that the `glm-5-think` file has only 3 trials for some tasks, so its pass^4 was not recomputable.) Issues #270 and #238 are prior acknowledged instances of published artifacts and metadata drifting from published scores.

**Confirmation and decomposition of the 1.0.1 banking re-grade.** On 1,920 paired simulations from five parseable leaderboard files, pre-1.0.1 to 1.0.1 is 0 pass-to-fail and 33 fail-to-pass, so "only upward" holds as scoped in the 1.0.1 notes (the separately disclosed `task_074` gold correction in #412 is the one downward change). Crossing code with data, task-definition data contributes exactly zero (the four data conditions agree to four decimals); the movement is entirely evaluator code, which independently agrees with the ablation in #408. Inside 1.0.1, the per-task `read_log_allowlist` is worth 39 simulations (2.03 points) in the strict direction relative to logging no reads at all. That is the quantity PR #405 asked for when it proposed reverting #329 "while we fully test how much the read-log allowlist change affects results". Restoring strict replay against 1.0.1 tools makes 15 to 23% of banking simulations unscorable and flips 20 pass-to-fail on the remainder. On the full 17-submission board (`submission.json` diff), mean +3.35, max +9.02, gemini-3-flash moves 9 -> 6, and 4 of 136 pairwise orderings reverse outright (a fifth pair, claude-opus-4-6 against gemini-3-flash, moves to an exact tie).

**Relation to #497, #493 and #498.** Issue #497 (open, 28 August 2026) reports a pre-registered, code-only audit of how tau2-bench aggregates trials: which pass^k denominator convention governs published figures, and whether the `INFRASTRUCTURE_ERROR` exclusion is correctly attributed. Only the question list was pre-registered; the audit itself is complete, and it executed nothing. Issue #493 and PR #498 cover the same denominator question. This report is independent and complementary: it was executed on public trajectories and measures what re-grading does to scores rather than what the code says. The two do not overlap in claims.

**Reproduction.** `repro/tau2/` in `repro_eval_instrument_2026-09-03.zip` (attached, and mirrored at https://github.com/YangzeLiu/eval-instrument-disclosure): `mkvenv.sh` builds one venv per release, `rescore.py` grades one file under one (code, data, flags) condition, `runmatrix.py` runs the matrix, `final_analysis.py` produces the transition tables. The solo-mode result above also reproduces with the shipped CLI alone: `TAU2_DATA_DIR=<release>/data tau2 evaluate-trajs <no-user-op file>`. Banking was graded with `retrieval_variant=bm25_grep` (no embedding key), validated by the exact 24.74 reproduction.

**Suggested changes.**
- Extend `is_solo_mode()` to recognise `llm_agent_solo_gt`, or key solo mode off something the trajectory records directly, so these files are re-graded in the mode they were produced in.
- Make lenient replay report the count of mismatched tool returns next to the score, and fail (or mark unscorable) above a threshold, so a file cannot silently re-grade to a fraction of its recorded score. A DB match rate of 3 of 456 is a signal the CLI already has.
- Make `--fresh-tasks` print which tasks' `evaluation_criteria` differ substantively from the embedded ones, document it in `docs/cli-reference.md`, and add a comparability note to the 1.0.0 airline entry.
- Re-upload the two banking trajectory files with the tool-message ids restored, so the 1.0.1 re-grade is reproducible from public data.
- Optionally, expose `--no-env-kwargs` and strict replay as documented flags so others can reproduce the decomposition above.
